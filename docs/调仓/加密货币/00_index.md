## 二、核心理念

### 1.1 什么是叙事板块轮动

加密货币轮动是**叙事驱动的主动组合管理策略**：资金沿「BTC → ETH → L1 → DeFi/L2 → Meme/高弹性补涨」的路径扩散（早期/中期/晚期可检验定义见 01 §3.3），超配即将轮入的叙事板块，低配已现流出信号的板块。

### 1.2 与追涨杀跌的本质区别

| 维度 | 追涨杀跌 | 机构级轮动 |
|------|---------|-----------|
| 决策依据 | 7 日涨幅榜 | 多因子评分 + 相对 BTC 强弱 + 轮动阶段 |
| 时间窗口 | 小时/日级别 | 周/月级别中期动量 |
| 仓位管理 | 满仓进出 | 分批加减、资金闭环（USDT） |
| 风控 | 无 | 硬性仓位上限、资金费率/解锁成本核算 |
| 执行节奏 | 一次性 | 分 1-3 日拆单（避开资金费率结算窗口） |

### 1.3 核心原则（不可违反）

1. **永远先卖弱，再买强** — 不同时进行买卖操作，资金必须闭环（06 §7.3.1.5）
2. **分批执行（约束在轮次，不约束单条指令）** — 一轮调仓默认分 1–3 日完成（7×24 可压缩至 1 日，但默认节奏不变；避开资金费率结算窗口，08 §9.2）；**单条指令是否拆分由 金额 / 事件窗口 / 动作类型 三条件决定（10 §11.2），「维持 / 小单 / 条件触发」型指令不得强行拆成多日**
3. **单板块上限 20%，单币上限 5%** — 硬性风控红线（分母 = 总预算 B = USDT 权益 × invest_mult，06 §7.3.1.2）
4. **中期动量优于短期爆发** — 加密里 **7 日 50% 暴涨是顶部信号而非买入信号**（11 §12.1）；20 日相对 BTC 强弱比 7 日涨幅更有意义
5. **大盘是总开关** — 风险偏好收缩（BTC 跌破 MA50 + BTC.D 快速上行，或 24h 全市场爆仓 > $5 亿）时**只卖不买**（01 §3.4）
6. **持仓只认 vnpy_mcp 实时返回** — 一律通过 vnpy_mcp 工具直读量化系统（系统必须正在运行）；**不使用任何 Redis 方面的工具**，也不得凭记忆或历史报告推断当前持仓
7. **轮动预测不当后视镜** — 方向来自「轮动阶段 + BTC.D/ETH-BTC + 板块相对强弱」（01 §3.5）；已走完的行情（Meme 7 日 >50%）只作防守/减仓依据，不作轮入依据
8. **调仓报告一次闭环** — 任务「生成调仓报告」以**最终报告通过 verify**（「校验」= 通过，exit 0）为唯一完成判据；中间产物（fund / gap / score / map / assemble 骨架 JSON）均不是任务完成，不得中途汇报「工具链跑通」即收工。详见 §四

## 四、任务执行与完成标准（一次闭环）

> 本节定义任务「生成调仓报告」**执行到什么程度才算完成**。执行该任务的 AI 必须从取数一直执行到 verify 通过并交付最终报告，**一次执行完，中间不停顿验收**。
> **外部对照验收细则**：报告级见 [13_验收要点.md](13_验收要点.md)；**工具/文档变更级**见 [14_变更验收要点.md](14_变更验收要点.md)（硬门 / 内容门 / 反模式 / 机读断言与容差 / 归因 / 判分）。

### 4.1 完成判据（以下全部满足，任务才算完成）

1. **最终报告 JSON** 具备 17 顶层字段（10 §11.2），且 `调仓指令` / `新增策略` 已按本轮决策填实：
   - 有调仓 → 每条指令含 目标持仓（= 目标资金 ÷ 现价，**按 `get_contract.min_volume` 向下取整**；加密永续可小数，禁套用美股整数取整，06 §7.3.1.2）/ 层级 S1–S5 / 分批计划 / 资金调整（初始资金 ≥ 目标资金 × 1.2，取 fund 策略槽位）/ 意图备注 / 调仓理由；
   - 无调仓（全部持仓缺口 < 2%×B 且无新仓名额）→ 两字段显式 `[]`，并在 `执行建议` 写明「本轮无调仓」及依据；
2. `持仓映射` S1–S5 与 `新增策略` / 资金汇总数值（Σ初始资金、目标仓位总和、目标组合策略数）已填；
3. `待人工确认` 逐条闭环：已填的删除，未填的保留并注明原因（不得把骨架原样清单当最终状态交付）；
4. **`verify --report <报告.json> --balance <最新USDT权益> --available <最新可用USDT>` → 「校验」= 通过（exit 0）**：
   - 「无法校验」→ 补齐数据重跑；「不通过」→ 按明细修正重跑；
   - 通过前必须核对：明细里「通过」项无**空洞通过**（指令集为空时 单币上限 / 分批自洽 / 高弹性上限 等检查无对象可查，天然「通过」；须确认指令数 > 0 或已按 4.1-1 写明「无调仓」后再采信）；
   - 通过前必须核对：**「不适用项数」= 0 或已逐条确认真属条件不满足**（工具会输出 `不适用项数` 与 `未执行检查项` 清单）。**「不适用」不是「通过」**；
5. 报告 JSON 落盘（路径明示），并向用户呈现关键内容（指令清单 / 资金汇总 / verify 结论 / 待人工确认残余）；
6. **`rebalance_audit.py`（源对账 + 时效门）→ 「校验」= 通过（exit 0）**（2026-09-15 新增，第 5 道闸）：
   - 覆盖项：`数据溯源块`（第 18 字段）/ `行情时效（K线末根 vs 取数日）` / `时效留痕` / `结构化引用对账`（板块评分·强弱清单·S1–S5 映射·资金汇总 ↔ score/score2/map/fund/gap）/ `空报告依据（0 指令时执行建议须写明无调仓）`；
   - **「提示项」≠「通过」**：未溯源数字、末根收盘价 vs 实时价偏差 > 1.5% 的标的，必须逐条确认出处并写入报告后方可交付；
   - 立门理由：`verify` 只覆盖报告**内部**自洽，输入时效与「报告 ↔ 来源」一致性必须另设一门（11 §12.7-7.3/7.4）。

### 4.2 标准执行顺序（管道；每步输出是下一步输入，不得在中间步停下汇报「完成」）

```
vnpy_mcp 取数（只读）：get_accounts / cta_strategies_get_all / get_positions / get_active_orders / get_all_contracts
  + cta_strategy_get_parameters_info（读 `volume_min_unit` 最小交易单位 → 铺开逐币档位表，与 get_contract.min_volume 交叉核对；12 §13.6-5）
  → fund（--balance --available，任务参数；--out 时同目录自动写 params.json —— v2.6.0 参数一次解析贯穿）
  → gate（v2.6.0：tier/mode/phase 机判 + 逐条证据/并列留痕 → gate.json；下游 score/score2/assemble --gate 继承；规格 = 01 附录 A）
  → 快照 JSON（策略名称/板块/分桶/当前市值/目标资金＝落地口径、可选 槽位资金＝决策口径（v2.6.0 qty-first）；目标资金来源 = §7.3.1.2 评分分配 或 §4.4 无评分最小闭环；板块/分桶映射 = 04 §6）
  → gap（--params tests/params.json：缺口 + 2% 不动 + 幅度截断 + 新仓名额 + 资金匹配）
  → score / score2 / map（板块·分桶评分与 S1–S5 映射；--gate 继承轮动阶段；无评分场景可跳过，但须按 §4.4 标注）
  → leaders（02 §4.2.5 龙头确认：逐板块核「T2 首位」20 日超额 ≥0；不通过 → 强制降中性；
           `--strong` 传 score 的强势板块清单 → 输出 确认后强势板块 / 降档板块；`audit --leaders` 对账）
  → assemble（17 字段骨架；数值自洽，指令/映射/文本仍空）
  → AI 填写：调仓指令 / 新增策略 / 持仓映射 / 分析摘要·目标分配·资金现状文本 / 风控校验
  → verify（独立复算报告内部自洽；「无法校验/不通过」→ 回到上一步修正，循环直至通过）
  → audit（源对账 + 时效审计：报告 ↔ fund/gap/score/score2/map/cycle/行情 逐项对账；
           不通过 → 修正后重跑；提示项须逐条人工确认）
  → 输出最终报告（§4.1-5）
```

### 4.3 反模式（出现即「任务未完成」，禁止当作完成汇报）

| # | 反模式 | 为什么不算完成 |
|:-:|------|------|
| 1 | fund / gap / score / map / exec / cycle 的 JSON 都成功输出就收工 | 它们是中间产物，报告尚未生成 |
| 2 | 只交付 assemble 骨架（`调仓指令` = []、`风控校验` = {}、verify 只能到「无法校验」） | 骨架按设计「只装配数值与结构，不产生任何判定」（10 §11.1），个币指令尚未产生 |
| 3 | verify「无法校验 / 不通过」被表述为「校验通过 / 管道验证完毕」 | 判定 = 工具输出「校验」字段，10 §11.1 校验门 |
| 4 | verify 明细全「通过」但报告 0 指令 / 0 映射 | 指令集为空时大量检查是空洞通过，「全绿」无覆盖度 |
| 5 | 把骨架的「待人工确认」原样当最终报告交付 | 待人工确认是过程态，交付前必须逐条闭环或注明挂起原因（§4.1-3） |

### 4.4 无评分最小闭环（任务显式跳过评分，或评分数据不可用时）

- 目标资金：现有持仓一律 维持（目标 = 当前市值）；新仓 ≤ `max_new`，资金平摊 fund 槽位；
- 报告 `执行建议` 必须写明「本报告目标资金非评分结论，未经 score/score2/map 全流程前不得作为执行依据」；`分析摘要.强势/弱势板块`、`强势/弱势子维度` 留空并进 `待人工确认`；
- verify 照常必须通过（数值口径与闭环检查不受影响）。

### 4.5 工具失效与数据不可得

- 工具代码失效：按「失效代码」铁律（10 §11.2）**只记录不改码**（工具 / 子命令 / 命令行 / 错误摘要 / 影响环节 / 降级处理），降级 = AI 手工计算 + 交叉复核，任务仍必须走到「最终报告 + verify 结论」；
- 量化系统未运行 / vnpy_mcp 取数失败：向用户报告并中止，**不得基于过期数据或记忆输出报告**（核心原则 6）；
- `get_all_contracts` 不可得 → 映射无法完成（04 铁律 4），停止并上报。

### 4.6 单一事实源与口径纪律

> 纪律来源：美股组 2026-09-15 事故根因——**同一概念被定义多次 → 相互漂移 → 报告自相矛盾**。币组自创建之日起继承。
