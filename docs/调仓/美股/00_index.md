## 二、核心理念

### 1.1 什么是板块轮动

板块轮动是一种**主动组合管理策略**，根据经济周期阶段在不同行业板块之间动态配置资金，超配有望跑赢的板块，低配可能跑输的板块。

### 1.2 与追涨杀跌的本质区别

| 维度 | 追涨杀跌 | 机构级轮动 |
|------|---------|-----------|
| 决策依据 | 当日涨幅榜 | 多因子综合评分 + 相对强弱 |
| 时间窗口 | 日线级别 | 周/月线级别中期动量 |
| 仓位管理 | 满仓进出 | 分批加减、资金闭环 |
| 风控 | 无 | 硬性仓位上限、止损规则 |
| 执行节奏 | 一次性 | 分多日拆单执行 |

### 1.3 核心原则（不可违反）

1. **永远先卖弱，再买强** — 不同时进行买卖操作，资金必须闭环
2. **分批执行（约束在轮次，不约束单条指令）** — 一轮调仓（整体）至少分 2-3 天完成，不单日大规模换仓；**单条指令是否拆分由 金额 / 事件窗口 / 动作类型 三个条件决定（10_AI调仓输出模板.md §11.2），"维持 / 小单 / 条件触发"型指令不得强行拆成多日**
3. **单板块上限 20%，单票上限 5%** — 硬性风控红线（分母 = 总预算 B = 权益 × invest_mult，06_策略资金分配.md §7.3.1.2）
4. **中期动量优于短期爆发** — 6-12 个月相对强弱比 5 日涨幅更有意义
5. **宏观是总开关** — 大盘系统性风险时只卖不买
6. **持仓只认 vnpy_mcp 实时返回** — 板块持仓分析一律通过 vnpy_mcp 工具直读量化系统（量化系统必须正在运行）；**不使用任何 Redis 方面的工具**（含 Redis 状态板、`enable_publish_status_redis` 发布的状态、Redis HTTP 代理、Redis 缓存），也不得凭记忆或历史报告推断当前持仓
7. **轮动预测不当后视镜** — 方向来自「宏观驱动 → 领先板块 → 滞后板块」映射 + 拐点信号（01_宏观环境定基调.md §3.5），只抓拐点或初期；涨幅榜只作确认，不作依据
8. **调仓报告一次闭环** — 任务「生成调仓报告」以**最终报告通过 verify**（「校验」= 通过，exit 0）为唯一完成判据；中间产物（fund / gap / score / map / assemble 骨架 JSON）均不是任务完成，不得中途汇报"工具链跑通"即收工。详见 §四 任务执行与完成标准

## 四、任务执行与完成标准（一次闭环）

> 本节定义任务「生成调仓报告」**执行到什么程度才算完成**。执行该任务的 AI 必须从取数一直执行到 verify 通过并交付最终报告，**一次执行完，中间不停顿验收**。

### 4.1 完成判据（以下全部满足，任务才算完成）

1. **最终报告 JSON** 具备 17 顶层字段（10_AI调仓输出模板.md §11.2），且 `调仓指令` / `新增策略` 已按本轮决策填实：
   - 有调仓 → 每条指令含 目标持仓（= 目标资金 ÷ 现价，向下取整）/ 层级 S1–S5 / 分批计划 / 资金调整（初始资金 ≥ 目标资金 × 1.2，取 fund 策略槽位）/ 意图备注 / 调仓理由；
   - 无调仓（全部持仓缺口 < 1%×B 且无新仓名额）→ 两字段显式 `[]`，并在 `执行建议` 写明"本轮无调仓"及依据；
2. `持仓映射` S1–S5 与 `新增策略` / 资金汇总数值（Σ初始资金、目标仓位总和、目标组合策略数）已填；
3. `待人工确认` 逐条闭环：已填的删除，未填的保留并注明原因（不得把骨架原样清单当最终状态交付）；
4. **`verify --report <报告.json> --balance <最新> --available <最新>` → 「校验」= 通过（exit 0）**：
   - 「无法校验」→ 补齐数据重跑；「不通过」→ 按明细修正重跑；
   - 通过前必须核对：明细里"通过"项无**空洞通过**（指令集为空时 单票上限 / 分批自洽 / T3 等检查无对象可查，天然"通过"；须确认指令数 > 0 或已按 4.1-1 写明"无调仓"后再采信）；
   - 通过前必须核对：**「不适用项数」= 0 或已逐条确认真属条件不满足**（工具会输出 `不适用项数` 与 `未执行检查项` 清单）。**"不适用"不是"通过"**——2026-09-15 事故中唯一的交叉核对项（组合重建）因存在未映射持仓而被静默跳过，汇总只显示"0 不通过 / 0 无法校验"，掩盖了报告的实质错误；
5. 报告 JSON 落盘（路径明示），并向用户呈现关键内容（指令清单 / 资金汇总 / verify 结论 / 待人工确认残余）。

### 4.2 标准执行顺序（管道；每步输出是下一步输入，不得在中间步停下汇报"完成"）

```
vnpy_mcp 取数（只读）：get_accounts / cta_strategies_get_all / get_positions / get_active_orders
  → fund（--balance --available，任务参数）
  → 快照 JSON（策略名称/板块/当前市值/目标资金；目标资金来源 = §7.3.1.2 评分分配 或 §4.4 无评分最小闭环）
  → gap（缺口 + 1% 不动 + 幅度截断 + 新仓名额 + 资金匹配）
  → score / score2 / map（板块·子板块评分与 S1–S5 映射；无评分场景可跳过，但须按 §4.4 标注）
  → assemble（17 字段骨架；数值自洽，指令/映射/文本仍空）
  → AI 填写：调仓指令 / 新增策略 / 持仓映射 / 分析摘要·目标分配·资金现状文本 / 风控校验
  → verify（独立复算；「无法校验/不通过」→ 回到上一步修正，循环直至通过）
  → 输出最终报告（§4.1-5）
```

### 4.3 反模式（出现即"任务未完成"，禁止当作完成汇报）

| # | 反模式 | 为什么不算完成 |
|:-:|------|------|
| 1 | fund / gap / score / map / exec / cycle 的 JSON 都成功输出就收工 | 它们是中间产物，报告尚未生成 |
| 2 | 只交付 assemble 骨架（`调仓指令` = []、`风控校验` = {}、verify 只能到「无法校验」） | 骨架按设计"只装配数值与结构，不产生任何判定"（10 §11.1），个股指令尚未产生 |
| 3 | verify「无法校验 / 不通过」被表述为"校验通过 / 管道验证完毕" | 判定 = 工具输出「校验」字段，10 §11.1 校验门 |
| 4 | verify 明细全"通过"但报告 0 指令 / 0 映射 | 指令集为空时大量检查是空洞通过，"全绿"无覆盖度 |
| 5 | 把骨架的 12 条「待人工确认」原样当最终报告交付 | 待人工确认是过程态，交付前必须逐条闭环或注明挂起原因（§4.1-3） |

### 4.4 无评分最小闭环（任务显式跳过评分，或评分数据不可用时）

- 目标资金：现有持仓一律 维持（目标 = 当前市值）；新仓 ≤ `max_new`，资金平摊 fund 槽位；
- 报告 `执行建议` 必须写明"本报告目标资金非评分结论，未经 score/score2/map 全流程前不得作为执行依据"；`分析摘要.强势/弱势板块`、`强势/弱势子板块` 留空并进 `待人工确认`；
- verify 照常必须通过（数值口径与闭环检查不受影响）。

### 4.5 工具失效与数据不可得

- 工具代码失效：按「失效代码」铁律（10 §11.2）**只记录不改码**（工具 / 子命令 / 命令行 / 错误摘要 / 影响环节 / 降级处理），降级 = AI 手工计算 + 交叉复核，任务仍必须走到「最终报告 + verify 结论」；
- 量化系统未运行 / vnpy_mcp 取数失败：向用户报告并中止，**不得基于过期数据或记忆输出报告**（核心原则 6）。

### 4.6 单一事实源与口径纪律

> 针对 2026-09-15 事故的根因：**同一概念被定义多次 → 相互漂移 → 报告自相矛盾**。
> 删章节治不了这个病，只有收敛「定义源」才行。

| # | 纪律 | 唯一权威 / 要求 |
|:-:|------|----------------|
| 1 | **板块身份与命名** | `scripts/domain_dict.json`（ETF 代码 ↔ 标准中文名 ↔ 简称/别名 ↔ 经济周期因子 ↔ cycles）是唯一权威。`score` 输出的 `板块` 为标准中文名，`score2` / `map` 同名可直接比对；`stock_pool.json` 的 `sub_sectors[*].sector` 必须取该标准名。**改板块命名只改这一个文件** |
| 2 | **决策矩阵** | `04_持仓映射与分层.md` §6.2（覆盖 板块 × 子板块 全部 9 种组合）。`03` §5.3.2 只引用、不重述 |
| 3 | **指标口径** | 每个派生指标必须写明**分子、分母、数据来源**（如 `调仓后总仓位_pct`：分母 = B，分子 = 调仓后持仓市值）。口径变更走单一事实源，**不做全文人工同步** |
| 4 | **手工覆盖留痕** | AI 手工复算 / 改写中间产物（榜单、分类、金额）时，必须在「数据缺失与冲突」注明"手工值 + 原因 + 依据公式"，并回写上游产物或明确标注偏离；**不得让手工值与工具值在报告里同权而无标记** |
| 5 | **一致性即校验** | `层级 ↔ 动作`、`分析摘要 ↔ 持仓映射`、`调仓后总仓位_pct ↔ 持仓明细`、`目标资金（决策口径）↔ 目标持仓 × 现价（落地口径）` 均由 `verify` 强制核对，任一项不自洽即「不通过」 |
| 6 | **禁止对门拟合** | 不得为使 `verify` 变绿而调整数值或口径并倒推理由。先按文档决策，再让校验门验证；`verify` 与文档冲突时记入「数据缺失与冲突」并暴露 |
